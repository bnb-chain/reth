# Snapshots

Reth publishes modular node snapshots at
[snapshots.reth.rs](https://snapshots.reth.rs). The snapshot UI lets you choose
minimal, full, or archive components and gives you the matching `reth download`
command.

Use snapshots when you want to avoid syncing from genesis. `reth download`
extracts the selected components into your Reth data directory. It also writes
`reth.toml` for the selected components if the file does not already exist;
after extraction, start `reth node` normally.

## Latest minimal snapshot

For the default minimal component set:

```bash
reth download -y

reth node
```

## Snapshot sizes

Snapshot download sizes are compressed and change with the selected profile,
selected components, and latest published block. The
[snapshots.reth.rs](https://snapshots.reth.rs) UI shows the estimated download
size for the current selection.

You can also list snapshot sizes from the CLI:

```bash
reth download --list
```

## Choose a profile

```bash
# Smallest built-in profile
reth download --minimal

# Full-node profile
reth download --full

# Archive profile
reth download --archive
```

## Custom components

Use the website or `reth download` flags to include specific components, such
as transaction files, receipts, state history, senders, or RocksDB indices:

```bash
reth download \
    --with-txs-distance 100000 \
    --with-receipts-distance 100000 \
    -y
```

## Existing complete snapshots

A publisher can also describe one existing `.tar.zst` or `.tar.lz4` file as a
complete snapshot bundle. Download it through the same command:

```bash
reth download --chain <chain> --manifest-url <manifest-url> --datadir <empty-directory>
```

A bundle restores the whole file, verifies extracted-file BLAKE3 checksums, and
preserves the producer's database checkpoints and included `reth.toml`. It does
not generate pruning settings or rebuild index checkpoints. Start the node with
the source snapshot's matching database, pruning, and static-file settings; if
`reth.toml` is absent, obtain those settings from the publisher.

Bundle manifests replace `components` with `bundle`, containing `profile`
(`full` or `archive`) and `archive` (the usual single-archive fields: `file`,
`size`, optional `decompressed_size`/`blake3`, and required `output_files`). Each
output needs its relative `path`, `size`, and BLAKE3 checksum. The supported
storage version is 2. Files must be under `db/`, `rocksdb/`, or `static_files/`,
or be the top-level `reth.toml`; `db/mdbx.dat` must be included. Never include
`components` in a bundle manifest: omitting it makes older clients reject the
new format instead of treating the snapshot as empty.

The selected chain must match the manifest, including with an explicit datadir.
`--full` or `--archive` may assert the corresponding source profile, but cannot
convert it. Component/range selections, `--minimal`, `--without-rocksdb`, and
`--prune-unlisted` are rejected. Already pruned history cannot be recovered by
labeling a full snapshot as an archive snapshot.

`--print-plan-json` lists one `bundle` archive. Verified files can be reused on a
rerun. As with modular manifests, the downloader caches the compressed archive
before extraction; budget disk space for both the archive and restored files.
Zstd windows up to `--long=31` are supported and may need up to 2 GiB of decoder
memory per concurrent archive. `--resumable=false` currently affects only the direct `--url` mode. Use a fresh
datadir for a new snapshot, or explicitly clear the previous data with `--force`.
